## 0. 一句話結論

教學設計本身完整且可實作，但它假設的平台能力與 SMAP 現況有落差。其中會讓活動完全跑不起來的阻塞性缺陷（答案金鑰外洩與學生無法作答，兩者同一個成因、互為表裡）**已於 2026-07-28 修復**。其餘落差分為「文件寫得比平台樂觀」「平台真的沒有、要新建」「平台已經有但文件沒寫」三類，逐條列於第 4 至 7 節。目前的最大待辦不再是那個缺陷，而是**學生帳號的開設方式**：決策已定為每人一個帳號，但平台沒有批次開帳號的路徑，且登入強制要求電子郵件已驗證，見第 4.2 節。

## 1. 被檢核文件在講什麼

這份 PDF 是「AI 教師數位分身」的第一階段教學規格，把一堂既有的國小四年級科學密室逃脫課（毛細現象／毛細偵探事務所）翻譯成 AI 可執行的教師功能模型。核心主張是：數位分身的定義是**功能等價**，不是模仿真人教師的個性；AI 負責可觀察的教學決策，人類保留安全、輔導、行為與技術的最終否決權。

主要內容：

- **§2 操作型定義**：五條功能等價準則（課程忠實度、互動忠實度、決策可追溯、界線忠實度、實證可分離性）。其中「決策可追溯」要求每一次介入都要記錄偵測到的狀態、套用的規則、提示層級與結果動作。
- **§3 教師功能模型**：TF-01 到 TF-12 共十二項功能，從備課檢查、先備知識喚起、敘事框架、規則說明、節奏轉場、進度監控、證據檢核、適性提示、協作教練、迷思回應、總結討論，到安全與失效升級。每項標明 AI 該做什麼、人類界線在哪。
- **§3.1 角色分配**：AI 教師（面向學生，負責提示、回饋、節奏）、診斷觀察者（靜默分類與建議，不與學生對話）、人類督導（安全、實體、技術、否決）、AI 同儕（本次實作排除，避免混淆比較）。
- **§4 課程生命週期**：S0 準備到 S6 結束共七個狀態，時間基準為 5 分鐘簡報 + 25 分鐘活動 + 10 分鐘總結。
- **§5 活動規格**：活動代號 SCI-WATER-CAP-01，四年級、中英雙語、3 至 6 人一組、每組一台共用平板（文字與語音）、拍照與 QR 掃描可用共用平板或個人裝置。任務為線性解鎖的 CAP-1 到 CAP-6：影片線索辨識現象、四種紙材毛細上升比較、日常應用辨識、紙花綻放取得隱藏指示、紅墨水染色圖樣判讀（答案為日本國旗）、彩虹大橋紙條搭橋（最終密碼為彩虹大橋）。
- **§6 逐題教學規格**：每題含教學目標、預期學生行為、可接受證據、常見錯誤、可能迷思、四階左右的題目專屬提示範例。
- **§7 學習者狀態與介入政策**：十種狀態（ON_TRACK、UNCERTAIN、SOFT_STALL、HARD_STALL、MISCONCEPTION、RANDOM_GUESSING、PARTICIPATION_IMBALANCE、OFF_TASK、UNSAFE_OR_SENSITIVE、SYSTEM_UNCERTAINTY）與對應 AI 回應。SOFT_STALL 定義為 45 秒無有意義動作或兩次同類錯誤，HARD_STALL 為 90 秒無進展、三次同類錯誤或兩次無效提示。文件自陳這些是工程預設值，非驗證過的心理學定義。
- **§7.1 提示階梯**：H0 等待、H1 後設認知、H2 注意力引導、H3 比較引導、H4 概念引導、H5 程序引導、H6 說明與補救，共七階，規則是永遠先用最不揭露的一階。
- **§8 協作協定**：以小組為單位對話，每題至少指派或輪換兩種角色（觀察者、器材管理、記錄者、解釋者、檢查者），接受最終答案前要求換一位成員解釋，在倫理許可下保留個別貢獻紀錄。
- **§9 總結規格**：六步驟總結序列（重建、命名、證據、辨異、遷移、反思）與最低學習證據要求。
- **§10 安全倫理界線**：實體安全、輔導與身心、行為、技術失效、內容不確定、隱私，六類各有必須的升級回應。
- **§11 最低軌跡資料**：十二種事件（session_started、task_presented、student_submission、submission_evaluated、state_classified、hint_delivered、task_advanced、human_intervention、safety_or_system_event、debrief_response、session_closed）及各自最低欄位。
- **§12 驗收標準**：其中一條為「實作清晰度：開發者能把每個任務與決策映射到結構化的 SMAP 狀態與事件，而不需自行發明教學法」。
- **§13 待確認事項**：Q1 至 Q10，其中 Q2 交付通道、Q3 真人教師可訪談、Q4 原始素材可重用已標為 CONFIRMED；Q1 班級規模、Q5 時間結構、Q6 競賽機制、Q7 證據擷取方式、Q8 器材安全清單、Q9 AI 揭露與同意、Q10 閾值校準仍待確認。

## 2. SMAP 平台現況（與本課程有關的部分）

以下是檢核當下的實際情形，供不熟悉 SMAP 的讀者建立判斷基礎。

**結構化活動（activities 有界上下文）共四個名詞：**

| 名詞 | 意義 | 建立者 | 範圍 |
|---|---|---|---|
| ActivityType | 活動模板：`key`、`name`、`payload_schema`（JSON Schema）、`validator_kind`、`validator_config`、`retention_days`、兩個可見性開關、`version` | 專案擁有者 | 專案 |
| ActivityActivation | 把某個 type 在某個聊天室「開啟」，一間房同時最多一個 | 房間建立者（即主持人） | 聊天室 |
| ActivitySession | 某一位受測者對該 type 的一次作答歷程，狀態 open 或 closed | 參與者 | 聊天室 |
| ActivitySubmission | 一次提交的權威紀錄：payload、`attempt_no`、驗證狀態、是否正確、錯誤類別、`sub_scores`、`latency_ms` | 參與者 | 聊天室 |

**評分機制：** 伺服器端權威評分，客戶端送來的分數一律不採信。驗證器有三種：`in_process`（同步，後端第一方程式碼）、`mcp`（沙箱容器，非同步）、`webhook`（外部 HTTP，非同步，且目前不支援上游認證）。平台目前**只內建一個** in_process 驗證器：`exact_match`，功能是比對 payload 某個欄位是否等於設定好的期望值。

**提交流程：** 提交時會在同一個交易內寫入 submission、一則系統訊息回音到聊天記錄、一筆稽核紀錄；交易提交後才發 WebSocket 事件與非同步驗證工作。提交必須在該 type 的 activation 為 active 時才被接受，且提交者只能替自己提交。

**反應式自動化：** 每次提交與每次驗證完成，會發出一個 workflow 訊號，內含 `activity_type_key`、`attempt_no`、`is_valid`、`error_class`，以及一個滾動彙總 `rolling.same_error_count`（預設 60 秒視窗內同一錯誤類別的次數）。workflow 引擎可用 `activity_event` 觸發器接住，用條件節點做門檻判斷（例如同類錯誤達 3 次），再驅動動作。

**Agent 與觀察者：** 房間可綁定多個 agent，各自有喚醒觸發器（每 N 則訊息、沉默 N 分鐘、@點名）。OBSERVER 角色的 agent 產出的是「觀察筆記」，不進聊天室、不觸發任何自動化，必須由人類按下放行才會出現在房間或送給特定 agent。自 R30.15 起，**所有** agent 的每一輪都會在系統提示中看到房間近期的結構化活動事件，不只觀察者；逐筆內容是否顯示由該 type 的 `expose_payload_to_agent` 控制。

**身分與加入方式：** 聊天室有四種可開關的存取層級（僅專案擁有者、專案成員、組織成員、訪客連結）。訪客連結不會建立帳號，訪客必須是已註冊使用者，連結只是把既有使用者記到該房間的訪客名單。訪客與專案成員是兩條獨立的授權路徑，互不隸屬。自 2026-07-28 起，訪客是完整的活動參與者（`[R30.26]`）。

**帳號的開設與登入（決定「每人一個帳號」的成本）：**

- 註冊需要一個格式合法且系統內唯一的電子郵件位址。
- **登入強制要求該信箱已完成驗證**：未驗證的帳號嘗試登入會直接被拒（`backend/contexts/identity/application/auth_service.py:328-329`）。驗證信是實際寄出的，因此信箱必須收得到信。
- 電子郵件驗證只在建立組織與建立專案時另有要求（`backend/shared_kernel/auth/permissions.py:366-372`）；聊天、開啟作答歷程、提交答案都不需要額外的驗證條件。也就是說**驗證只卡在登入這一關**，過了就不再是障礙。
- Google 登入所建立的帳號會直接標記為已驗證（`auth_service.py:533`），不需要收驗證信。
- 平台**沒有批次建立使用者的路徑**。唯一能建立「預先驗證」帳號的工具是 `smap.bootstrap.create_admin`，但它同時把該帳號寫進 `admins` 表（`backend/smap/bootstrap/create_admin.py:102-112`），會賦予平台管理權限，不能拿來開學生帳號。管理端 API 既不能建立使用者，也沒有覆寫驗證狀態的功能。
- 忘記密碼的復原流程走寄信重設。若學生帳號用的是收不到信的位址，密碼一旦遺失就只能由具資料庫權限的人介入。

**其他相關能力：** 聊天訊息支援附件（含病毒掃描、隔離、文字抽取）；對話可匯出為 markdown、json 或 pdf；LLM 取樣參數 `temperature`、`top_p`、`seed` 可在 agent 設定，因此評分可重現；活動資料可設定研究保留天數，房間清除會跳過保留期未到的資料；介面語系有英文與繁體中文兩種。

**前端活動介面：** 聊天室右側有「活動」分頁。主持人可從既有 type 下拉選單啟動與結束；參與者按「加入」開啟自己的 session，透過 ActivityHost 作答，作答介面是專案自寫的 plugin，若無 plugin 則退回通用的 JSON Schema 表單。通用表單支援的欄位型別只有字串、數字、布林、單選列舉、多選列舉，其他型別降級為 JSON 文字框。

**活動類型的兩種投影（2026-07-28 起）：** 擁有者看到的是完整編輯紀錄（含 `validator_config`）；參與者看到的是公開投影，只有識別碼、鍵值、顯示名稱與 payload schema 四個欄位。公開投影同時嵌在啟用狀態的讀取回應與啟用廣播裡，另有一支房間層端點供廣播漏接時補水。`validator_config` 對非擁有者一律遮蔽，且不出現在任何房間層回應或即時通道。

## 3. 阻塞性缺陷（已於 2026-07-28 修復）

本節保留缺陷的完整描述，因為它是新增需求 `[R30.25]`、`[R30.26]` 的理由，也是日後檢視同類問題的參照。修復內容記於本節末。

### BUG-1：答案金鑰會發到學生瀏覽器，且與「學生能否作答」互斥

這是一個缺陷，不是設定問題，也不是可以繞過的教學設計選擇。成因是三件事串在一起：

1. 內建的 `exact_match` 驗證器把**正確答案存在 `validator_config.expected`**（`backend/app/plugins/activity_validators.py:37`）。以本課程為例，就是「日本」「彩虹大橋」這些關卡密碼。
2. 活動類型的 API 回應模型原樣回傳整個 `validator_config`，**沒有任何遮蔽**（`backend/app/api/v1/activities.py:85-97`、`:172-185`）。
3. 取得活動類型的唯一端點 `GET /api/projects/{project_id}/activity-types` 只檢查專案成員資格（`backend/app/api/v1/activities.py:364`）。

而參與者的作答介面**正是**靠這支端點取得 `payload_schema` 來渲染表單（`frontend/src/slices/activities/components/ActivityPanel.vue:52`）。房間層的 activation 端點只回傳 `activity_type_id`，不含 schema（`backend/app/api/v1/activities.py:115-122`、`:200-209`），所以沒有第二條路。

由此產生兩種互斥的結局，兩種都不能上課：

- **學生設為專案成員**：作答介面正常，但學生打一次那支 API 就拿到全部六關答案。密室逃脫的全部價值歸零。
- **學生用訪客連結加入（非專案成員）**：該 API 回 403，前端 `types` 為空，`activeType` 為 null，而作答區塊被 `v-if="activeType"` 包住（`frontend/src/slices/activities/components/ActivityPanel.vue:139`），因此「加入」按鈕與整個作答介面**都不會渲染**。學生看得到活動名稱，但完全無法作答。

**根本原因**：同一個回應模型（`ActivityTypeOut`）同時服務「擁有者的編輯紀錄」與「參與者的渲染契約」。因為唯一的投影是編輯紀錄，它只能架在專案層端點上；於是拿得到的人看到答案，拿不到的人整個作答介面消失。

### BUG-2（同源，隨 BUG-1 一起修）：訪客無法參與結構化活動

如上所述，這是 BUG-1 的另一面。單獨描述是因為它的症狀完全不同（不是外洩而是功能失效），排查時容易被當成兩個問題。兩者必須一起修，否則修好其中一邊會讓另一邊惡化：把學生升為專案成員可以修好「無法作答」，但會直接造成答案外洩。

### 修復內容（2026-07-28 完成）

拆開那個回應模型，兩類讀者各有自己的投影：

1. 新增參與者用的公開投影（識別碼、鍵值、顯示名稱、payload schema），不含 `validator_config` 及任何編輯欄位。
2. 新增房間層端點取得單一活動類型的公開投影，授權走房間存取鏈，並做跨專案隔離（他專案的類型一律回 404）。
3. 同一份公開投影嵌入「目前啟用中的活動」讀取回應與 `activity.activation.started` 廣播，讓晚到與重連的參與者自動補水。
4. 專案層列表對非擁有者遮蔽 `validator_config`；註冊與編輯本來就是擁有者限定，維持不變。**擁有者仍取得真實內容這一點是承重的**：編輯表單是從這支列表預填的，若對擁有者也遮蔽，儲存時會把 `validator_config` 洗成空值。
5. 前端參與者路徑不再依賴專案層列表，改讀啟用狀態內嵌的投影，漏接時退回房間層端點；專案層列表僅供主持人的啟動下拉選單使用，其失敗不再阻斷參與者。

新增需求 `[R30.25]`（`validator_config` 對非擁有者機密、不得出現在任何房間層或即時通道）與 `[R30.26]`（參與者的渲染契約走房間存取鏈；訪客為完整參與者）。

**尚未完成的一項**：修復當時開發環境的 Docker 無法連線，訪客完整流程與「廣播漏接後補水」兩條只在測試層驗證，未實機跑過。正式上課前必須在可用的環境補做一次端到端實機驗證。

## 4. 文件敘述與平台現況衝突（文件需要修改）

### 4.1 45 秒與 90 秒的僵局閾值，目前表達不出來

文件 §7 把 SOFT_STALL 定為 45 秒無有意義動作、HARD_STALL 為 90 秒無進展，並在閾值說明中稱這些是「工程預設值，必須保持可設定」。實際上：

- 唯一的沉默型觸發器單位是**分鐘**，下限為 1 分鐘（`backend/contexts/orchestration/domain/models.py:115`），掃描排程每 30 秒執行一次（`backend/app/workers/main.py:336`）。45 秒設不出來，90 秒只能近似成 1 分鐘或 2 分鐘。
- 活動事件觸發器只在**提交或驗證完成**時發訊號。「45 秒內什麼都沒送出」本質上不是事件，不會產生任何訊號，現有的反應式規則接不到。

文件應改寫為：時間型僵局偵測需要新機制，或明確接受最小粒度 1 分鐘。不是「調個參數」而已。次數型門檻（連續同類錯誤 N 次）則是現成可用的，平台已內建 60 秒視窗的同錯誤計數。

### 4.2 共用平板與個別貢獻紀錄：已決定採每人一個帳號

**原本的衝突。** 文件 §5.1 設定「3 至 6 人一組，每組一台共用平板」，同時 §8 要求「在倫理許可下保留個別貢獻紀錄」，§7 要求偵測 PARTICIPATION_IMBALANCE（一人主導或某人零貢獻）。平台上，作答歷程綁在單一使用者身上，而且系統強制只能替自己提交（`backend/contexts/activities/application/submission_service.py:88`）。一組共用一個帳號的話，該組所有提交的產生者都是同一個人，聊天訊息同理，個別貢獻與參與失衡在資料層完全分辨不出來。

**決定（2026-07-29）：每位學生一個帳號。** 個別貢獻紀錄與參與失衡偵測因此在資料層成立，`[R30.26]` 的訪客參與模型也讓學生用連結加入而不需要專案成員資格。代價是以下兩項新工作，都必須在第一次上課前處理完。

#### 4.2.1 帳號開設：目前沒有可用的批次路徑

平台的登入強制要求電子郵件已驗證，而驗證信是實際寄出的（詳見第 2 節「帳號的開設與登入」）。因此一個班約 30 個學生帳號，只有三條路可走：

| 方案 | 作法 | 代價與風險 |
|---|---|---|
| A. 學校 Google 帳號 | 學生以校方 Google Workspace 帳號登入，系統自動標記為已驗證，不必收驗證信 | 最省事，前提是學校有發帳號給四年級學生且允許用於校外服務。需確認校方資訊政策與家長同意的涵蓋範圍 |
| B. 可收信的真實信箱 | 每位學生一個能收信的位址（家長信箱加子地址、或校方信箱），走正常註冊與驗證 | 30 次人工註冊與驗證，課前作業量大；若用家長信箱，家長會收到平台信件，需事先說明 |
| C. 新增批次開帳號的功能 | 做一支管理端的批次建立學生帳號功能，建立時直接標記為已驗證，並產生初始密碼 | 需要開發。優點是可控、可重複用於後續每一個班，也解決忘記密碼只能改資料庫的問題。若這個研究會持續多學期，這是唯一會攤平成本的選項 |

不建議直接改資料庫塞使用者：那會繞過稽核與所有應用層不變條件，且沒有任何測試涵蓋。

**建議**：先確認方案 A 是否可行（一通電話的事），不可行就評估 C。方案 B 只適合單次試教。

#### 4.2.2 裝置歸屬：每人一個帳號與每組一台平板是有張力的

一個瀏覽器同時只能登入一個帳號。若一組四人共用一台平板，四個人的提交要各自歸屬，就得在活動進行中反覆切換登入，這在教室現場不可行，也會破壞 §4 的時間結構。實務上只有三種收法：

1. **每人一台裝置**（或至少每人一個瀏覽器工作階段）。個別歸屬完全成立，但器材需求大幅提高。
2. **共用平板只作為「小組共同產出」的提交口，個人貢獻改由聊天訊息承載**。此時活動提交的 `producer_user_id` 是操作平板者，個別貢獻要從對話記錄推估，`PARTICIPATION_IMBALANCE` 只能靠訊息量與內容判斷，精確度下降但仍可行。
3. **混合**：共用平板負責需要器材操作的關卡（CAP-2、CAP-4、CAP-6），個人裝置負責文字作答與解釋（CAP-1、CAP-3、CAP-5）。

文件 §5.1 目前已寫「拍照與 QR 掃描可用共用平板或個人裝置」，表示個人裝置本來就在畫面裡。**需要教學端明確定調選哪一種**，因為它同時決定器材清單、§8 的角色輪換怎麼落實、以及參與失衡偵測的資料來源。

### 4.3 語音與 QR 掃描不被平台支援

文件 §5.1 把交付通道描述為「共用平板，文字與語音；拍照與 QR 掃描可用共用平板或個人裝置」，並在 §13 Q2 標為 CONFIRMED。

平台實況：

- **語音**：前端沒有任何語音輸入或輸出的實作。互動全部是文字與 markdown。
- **QR 掃描**：沒有實作。
- **照片作為證據**：聊天訊息可以帶附件，但活動提交的表單只支援字串、數字、布林、單選與多選列舉，其他型別降級為 JSON 文字框（`frontend/src/slices/activities/components/schemaFields.ts:10`）。照片無法成為被驗證器評分的欄位，只能貼在聊天室裡讓人或 agent 目視。
- **影片**：沒有教材資產管理或內建播放器，CAP-1 的核准影片只能靠外部連結。

Q2 的 CONFIRMED 是對**教學現場載具**的確認，不是對平台能力的確認。文件必須把這兩件事分開，否則實作端會踩空。Q7（證據擷取）的答案其實已經被平台限定：第一版只能是文字與選項，照片走聊天室由人或 agent 目視判讀。

### 4.4 TF-07 證據檢核超出現有驗證器能力

文件 §6 的可接受證據幾乎全是語意判斷：CAP-1 要求「說出毛細現象，並描述向上或穿透材料的移動，且沒有抽送或倾倒」；CAP-2 要求「提出觀察到的順序，並引用可比較的起始條件或可測量距離」；CAP-6 要求「說出彩虹大橋，並解釋顏色如何經由紙的狹縫移動」。

平台內建的唯一驗證器是 `exact_match`，只能比對某欄位是否等於期望值，做不到上述任何一條。另外兩種驗證器（沙箱 MCP 與外部 webhook）是非同步的，webhook 目前還不支援上游認證。**平台沒有「LLM 判定」這種驗證器類型。**

若要 AI 判定答案，只有兩條路：

1. 新寫一個第一方 in_process 驗證器（後端程式碼，自行呼叫 LLM 並處理不確定性）。
2. 讓 agent 讀活動資料後自行判斷，但這樣不會寫回 `is_valid` 與 `sub_scores`，等於沒有可查詢、可重現的評分紀錄，也就無法支撐 §2.2 的決策可追溯與後續的評分一致性檢驗。

文件 §12 的驗收條件「開發者能把每個任務與決策映射到結構化的 SMAP 狀態與事件，而不需自行發明教學法」，以現況是通不過的。建議把這條拆成「教學面完備」與「平台面可映射」兩條，後者附一張映射表，逐項標示已有、需設定、需新建。

### 4.5 角色分配與實際的多 agent 行為不符

文件 §3.1 假設 AI 教師與診斷觀察者分工明確、發言有序。平台上，房間綁定的每個 agent 各有自己的喚醒觸發器，預設是每 1 則訊息就觸發，也就是 AI 教師與觀察者會**同時**對每一則學生訊息起反應，沒有中央發言仲裁。

要達到文件描述的秩序，必須把 AI 教師設成 @點名驅動，或用 workflow 有向圖把整條流程編排起來。這是硬性的設定需求，應寫進文件的實作註記，否則第一次上課就是兩個 AI 搶話。

另外，§7 表格把「偵測狀態」與「AI 回應」寫在同一列，容易讓實作者誤以為是同一個 agent 的事。平台上診斷觀察者的輸出是觀察筆記，不進聊天室、不觸發自動化、需人類放行，因此**它不能直接發提示**。偵測與發話必須是兩個 agent，中間靠 workflow 規則或人類放行銜接。文件應明說這個分工限制。

### 4.6 診斷資料的可見範圍與文件假設不同

文件隱含「只有診斷觀察者看得到分析資料」。實際上自 R30.15 起，**所有** agent 的每一輪都會看到房間近期的結構化活動事件（`backend/contexts/agents/application/runtime/turn_engine.py:2012-2017`），不只觀察者。

若要維持 §3.1 的角色分工，必須用該 type 的 `expose_payload_to_agent` 開關明確關掉，否則 AI 教師也會直接讀到全部提交資料。這會反過來影響 §2.2 的實證可分離性，因為 AI 組的資訊環境會與設計描述不一致。

## 6. 文件應提及而未提及（平台已具備，可以直接採用）

這些是現成的能力，文件目前把其中幾項列為待確認，或完全沒寫。

1. **研究資料保留已有具體機制。** Q9 把資料保留列為待確認，但平台已實作：活動類型可設定保留天數，每筆提交在建立時就算出保留到期日，房間清除會跳過保留期未到的資料。決策其實只剩「填幾天」。**重要限制**：保留到期日在提交當下就寫死，事後修改類型的保留天數**不會回溯**（`backend/contexts/activities/application/submission_service.py:113-118`）。因此這個數字必須在收第一筆資料前就決定。

2. **AI 身分揭露已是房間層級的設定。** Q9 詢問「適用哪些 AI 揭露要求」時，可以直接說平台已有這個開關。

3. **LLM 取樣可重現性已實作。** `temperature`、`top_p`、`seed` 可在 agent 設定上指定。文件 §2.2 的決策可追溯與 §12 完全沒提 LLM 輸出的隨機性；日後要做「AI 教師 vs 真人教師」比較或評分一致性檢驗（例如 Cohen's Kappa），固定取樣參數是前提，應寫進文件。

4. **提交是伺服器端權威評分**，客戶端送來的分數一律不採信。§2.2 可以把這一點寫成既有保證。

5. **每次提交都有伺服器指派的單調遞增嘗試序號與延遲毫秒數**；反應式訊號已內建 60 秒視窗的同錯誤類別計數。§7 定義次數型門檻時可以直接對齊這個既有結構。

6. **內容曝光有兩個獨立開關**：一個控制 agent 是否看得到提交內容，另一個控制是否把內容寫進聊天記錄，且後者只在前者開啟時生效。這對「AI 不得提前洩漏答案」與 §10 的隱私條款有直接關係，值得在 §10 明確引用。注意這兩個開關管的是**學生提交內容**，與第 3 節的答案金鑰外洩是兩回事，當時不能指望它擋那個問題，現在也不是靠它擋住的（金鑰機密性由 `[R30.25]` 的投影拆分負責）。

7. **介面語系已有英文與繁體中文**，與 §5.1 的中英雙語相符。agent 的產出語言由提示詞控制，不受語系限制。

8. **研究效度上有一個現成的辯護**。§2.2 的實證可分離性要求「不加額外 AI 角色以免混淆比較」，但 §3.1 同時放了 AI 教師與診斷觀察者兩個 AI，人類教師組沒有等價的靜默診斷者，表面上兩組資訊環境不對等。平台面的事實是：觀察筆記不進聊天室、預設需人類放行才可見，對學生完全不可見，因此不構成處理差異。這個論證站得住，但文件沒寫，審查時會被追問。

## 7. 成本、時間與當日運作（文件完全沒有這幾節）

### 7.1 成本

平台是自帶金鑰模式，研究團隊自付。預設的記憶模式每一輪會重送完整對話歷史（約 100 則），沒有提示快取，也沒有花費上限。一堂課 40 分鐘、每組一間房、每則訊息喚醒兩個 agent，一個班五到六組同時上課時的 token 量與供應商速率限制，目前沒有被估算過。文件應該補一節成本與模型選擇（例如固定使用低價快速模型、改用精簡記憶模式、降低脈絡上限、改為點名驅動）。

### 7.2 時間預算

45 秒的提示視窗要塞進：學生停止動作、系統偵測（沉默掃描每 30 秒一次，門檻最小 1 分鐘）、LLM 回合延遲、若使用非同步驗證器再加上容器啟動的秒級延遲。這個時間帳算不出來，45 秒就不該寫進規格當作可實作的閾值。

### 7.3 當日失效模式

- 主持人結束活動時**不會關閉學生已開啟的作答歷程**，只是擋住新的提交。這是刻意的設計取捨，但文件的狀態機 S4、S6 假設有明確收束。
- 活動狀態靠 WebSocket 廣播加上重新取得補水。平板休眠、換網路的重連路徑平台有處理，但沒有針對「活動進行中斷線」做過行為驗證。
- 若後端以開發模式的密鑰服務執行，重開機後所有供應商金鑰將無法解密。§10 的「提供核准的備援方案，否則通知人類並保留狀態」需要一份具體的降級腳本，並在正式上課前做一次完整演練。

## 9. 更正紀錄

本節記錄檢核過程中先前得出、後來被推翻的判斷，避免後續讀者沿用錯誤結論。

**更正 1：CAP-1 至 CAP-6 的任務串接並非做不到。**

先前判斷為「一間房同時只能有一個啟用中的活動，所以六關要人類手動啟動與結束六次」。這是錯的。正確做法是整堂課只註冊**一個**活動類型，把關卡代號（CAP-1 至 CAP-6）做成 payload schema 裡的一個列舉欄位，六關的推進由專案自寫的前端 plugin 處理，主持人整堂課只需啟動一次。

真正的限制要重新表述為：

- 伺服器端沒有順序強制（見第 5 節最後幾列），解鎖只是前端慣例。
- 六關共用同一組類型層設定：可見性開關、保留天數、以及同一個驗證器。
- 嘗試序號是以作答歷程為單位遞增，不是以關卡為單位。「同一關同類錯誤 3 次」要靠錯誤類別欄位或從 payload 反推，不能直接用嘗試序號。

**更正 2：agent 完全不能啟動活動，這說法太絕對。**

理論上 agent 可以透過對外請求工具呼叫 SMAP 自己的公開 API 來啟動活動。但：出站代理封鎖私有位址、回送位址與連線本地位址，本機或內網部署直接不通；需要具備房間建立者權限的憑證；而對外請求工具的上游認證憑證封存目前是未完成項。結論應為「可行但作法不乾淨，且需先解決憑證保管」，而非「不可能」。
