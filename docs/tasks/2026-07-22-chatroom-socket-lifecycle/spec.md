# Chatroom socket lifecycle: client heartbeat, cap-rejection storm, and typing retraction

## 1. Summary

Three defects in the WebSocket lifecycle, taken together because the first one masks the third and because all three live in the same two files. The client never sends the periodic `ping` the server's idle reaper is written around (`backend/shared_kernel/realtime/connection.py:49-54`), so every socket on the platform is closed with 1013 after 120 seconds of quiet and immediately reconnects, producing perpetual ~121 second churn per socket (F-1). Separately, a user who exceeds the per-user socket cap is accepted and then closed, which the transport reads as a successful connection, so the backoff is reset on every rejection and the channel retries forever at exactly 1 Hz without ever reaching the degraded state that would engage the REST polling fallback (F-4). Finally, a closing connection never retracts its own `typing.start`, so when the typing user has a second connection in the room the indicator is never cleared for other members (F-18); today that is hidden because `resyncPresence` clears typing on every reconnect, and F-1 supplies a reconnect every two minutes. Fixing F-1 alone would therefore convert F-18 from invisible into permanent, which is why the three are one change.

**Scope note (2026-07-24).** Q-5 was answered "build it", which adds a fourth, non-defect deliverable: a distinct connection-limit pill state so a capped user is told the actionable thing (close a tab) instead of only the generic degraded banner. It rides on the F-4 fix — the stability window is what makes a cap rejection distinguishable in the first place — and widens the touched-file set beyond the two named above to `ChatroomHeader.vue`, `useChatroomSocket.ts`, both conversation locale files and the pill table in `docs/UI/07-conversation.md`. Details in §7 ("Q-5 addition"), decisions in Q-5 and Q-7.

## 2. Observed vs Expected

**F-1 - idle reaper kills every live socket**

- **Observed** - `connection.py:253-269` bounds `ws.receive_text()` with `_IDLE_TIMEOUT_SECONDS = 120.0` (`:54`) and closes 1013 "idle timeout" when no inbound frame arrives. No client ever sends one: the only outbound frames in the frontend are `typing.start`/`typing.stop` (`frontend/src/slices/conversation/views/ChatroomView.vue:632,637`, user-driven) and `refresh` (`frontend/src/shared/transport/ws-manager.ts:286`), scheduled at `exp - 60s` against `access_ttl_seconds = 15 * 60` (`backend/app/config/settings.py:154`), roughly 840 seconds. The server's `ping`/`pong` handler (`connection.py:298-300`) has no caller. Every socket therefore closes at t=120s and `ws-manager.ts:152-156` reconnects at the 1 second floor.
- **Expected** - the module contract states a live client sends periodic `ping` frames (`connection.py:49-54`), and `backend/contexts/conversation/infrastructure/presence.py:31-35` builds on that invariant directly: `_CONN_TTL_SECONDS = 150` is chosen to exceed the 120 second idle window because "a live connection sends at least one frame per idle window and refreshes the conns SET on each, so this TTL never lapses under it". The reaper is intended to collect half-open sockets only (`connection.py:50-53`), not live ones. Intent sources: R13.19 (`REQUIREMENTS.md:683`), R13.20 (`:691`), `docs/implement/F-chat-realtime.md:173-175`.

**F-4 - per-user cap produces an unbounded 1 Hz retry**

- **Observed** - `connection.py:212-218` accepts the socket and then closes it with 1013 "per-user WS cap reached". The browser completes the 101 handshake before processing the close, so `onopen` fires and `ws-manager.ts:135-141` resets `backoff = INITIAL_BACKOFF_MS` and `consecutiveFailures = 0`. The subsequent `onclose` (`:152-156`) schedules a retry at the freshly reset `backoff`. The cap is per user, not per path (`connection.py:90-91`), and each chatroom tab opens two sockets (`useChatroomSocket.ts:45` plus `/user/{id}` via `frontend/src/shared/composables/useBanKickGuard.ts:33`, `frontend/src/slices/notifications/composables/useNotificationsSocket.ts:34`, `frontend/src/slices/conversation/composables/useObservations.ts:139`, deduplicated to one socket by `wsManager.channel`), so three tabs reach 6 against `ws_concurrent_per_user: 5` (`settings.py:385`).
- **Expected** - R19.03 (`REQUIREMENTS.md:876`) refuses excess connections; R24.14 (`:1852`) centralizes "reconnect, backoff, auth refresh" in the transport; `docs/UI/12-shared-patterns.md:428-445` specifies exponential backoff and, after 3 failed reconnects, a fall back to 10 second REST polling with a banner. A capped user should settle into a slow retry with the polling fallback engaged, not oscillate live/reconnecting at 1 Hz forever.

**F-18 - typing indicator is never retracted by a closing connection**

- **Observed** - `backend/app/api/ws/chatroom.py:130-142` publishes `presence.left` only when the closing socket was the user's last (`presence.py:139-141` returns `left=False` otherwise) and never publishes `typing.stop` at all. The client clears typing only on `typing.stop` or `presence.left` (`useChatroomSocket.ts:216-224`); there is no server-side typing TTL (`chatroom.py:75-84` merely republishes) and no client-side expiry (`stores/conversation.ts:41-52` are plain set operations).
- **Expected** - R13.19 (`REQUIREMENTS.md:683`) lists typing indicators as room presence state; `docs/UI/07-conversation.md:538-567` specifies the indicator as transient state driven by `typing.start`/`typing.stop`, hidden when nobody is typing. A connection that goes away has stopped typing by definition.

## 4. Reproduction

Preconditions for all three: a running stack (`deploy/compose/`), one org with a project, one chatroom the test user can read, default settings (`ws_concurrent_per_user: 5`, `access_ttl_seconds: 900`).

**F-1** (deterministic, no second actor)

1. Log in and open any chatroom. Do not type.
2. Watch the browser network panel's WS entry and the backend log.
3. At t=120s the server logs `ws_idle_timeout` (`connection.py:264-267`) and closes 1013. The client reconnects about one second later (`ws-manager.ts:225-228` with `backoff = 1000`).
4. Other room members observe the presence pill for this user flap off and on (`chatroom.py:137-140` then `:118-121`).
5. The cycle repeats indefinitely at roughly 121 seconds. `/ws/user/{id}` is affected identically; simply being logged in is enough.

**F-4** (deterministic)

1. As one user, open three chatroom tabs. Each tab holds `/chatroom/{id}` plus the shared `/user/{id}` channel, so the sixth socket exceeds the cap of 5.
2. Observe, once per second and without end: one `POST /api/auth/ws-ticket`, one WS handshake, one `zremrangebyscore`/`zadd`/`zcard`/`expire`/`zrem` sequence on `ws:conns:{user}` (`connection.py:139-152`), one `WS_PER_USER_REJECTIONS` increment (`:213`).
3. The connection pill on the third tab oscillates between live and reconnecting and never reaches degraded, so REST polling never starts (`useChatroomSocket.ts:359-363`).
4. Closing one tab resolves it; nothing else does.

**F-18** (deterministic once F-1 is fixed; masked today)

1. User U opens the same room in two tabs. User V is in the room in another browser.
2. In tab 1, U types one character. `typing.start` is sent (`ChatroomView.vue:632`) and V sees "U is typing".
3. Within the 3 second debounce (`ChatroomView.vue:620,636-639`), kill tab 1's network (devtools offline, or kill the tab process so no unmount `typing.stop` at `useChatroomSocket.ts:384` is sent).
4. `on_close` runs for tab 1's socket but `presence.leave` reports `left=False` because tab 2 remains (`presence.py:139-141`), so neither `presence.left` nor `typing.stop` is published.
5. On today's build V's indicator clears at V's next reconnect, within two minutes (`useChatroomSocket.ts:111`). Apply the F-1 fix alone and it never clears. This is the regression the co-scoping exists to prevent, and step 5 is the assertion to run before and after.

## 5. Root Cause Analysis

**F-1.** Chain: the reader arms `asyncio.wait_for(ws.receive_text(), timeout=_IDLE_TIMEOUT_SECONDS)` (`connection.py:258-262`) -> no client code path ever produces an inbound frame on a quiet socket, because the only senders are user-driven typing (`ChatroomView.vue:632,637`) and the ~840 second token refresh (`ws-manager.ts:242-256,286`) -> `TimeoutError` -> `_request_close(1013, "idle timeout")` (`:268`) -> `_cleanup` runs `on_close`, publishing `presence.left` and possibly `_notify_presence(has_live_users=False)` (`chatroom.py:130-142`) -> `onclose` on the client schedules a reconnect at the 1 second floor (`ws-manager.ts:152-156,225-228`) -> `on_open` republishes `presence.joined` and may re-fire the presence transition (`chatroom.py:111-128`), and the connect handler issues three HTTP resyncs (`useChatroomSocket.ts:353-355`).

**Root cause: the client half of the documented heartbeat protocol was never implemented.** The server side is complete and inert (`connection.py:298-300` has no caller). Protocol-level WebSocket pings do not substitute: the audit verified against uvicorn and starlette that only data frames become an ASGI `websocket.receive`, so the transport keepalive keeps TCP healthy while the application reaper does the killing. Aggravating factors, not causes: the 1 second reconnect floor (`ws-manager.ts:33`) makes the churn tight, and `presence.py:35`'s TTL choice depends on the missing heartbeat, so presence liveness is currently maintained only as a side effect of the churn.

**F-4.** Chain: `_register_user_connection` returns False (`connection.py:212`) -> `ws.accept()` then `ws.close(1013)` (`:216-217`) -> the 101 upgrade has already completed, so the browser fires `onopen` -> `ws-manager.ts:136-137` sets `backoff = INITIAL_BACKOFF_MS` and `consecutiveFailures = 0`, and `:138` clears degraded -> `onclose` (`:152-156`) calls `scheduleReconnect` -> `:221` increments `consecutiveFailures` to 1, below `DEGRADED_THRESHOLD = 3` (`:38`), so no degrade -> `:225-228` arms the timer at the just-reset `backoff` of 1000 ms -> `:229` doubles the stored value to 2000, which the next `onopen` immediately resets to 1000 again.

**Root cause: the transport treats "the HTTP upgrade completed" as proof of a successful connection.** Being precise about "unbounded 1 Hz", because it determines the shape of the fix: the backoff curve at `ws-manager.ts:229` is *not* broken. It doubles correctly and is capped at `MAX_BACKOFF_MS = 30_000` (`:34`), and the degrade counter at `:221-224` works. What is broken is the reset predicate at `:136-138`. Every rejection satisfies it, so the doubling at `:229` is undone before it can ever be read, the failure counter is zeroed before it can ever reach 3, and the steady state is exactly `INITIAL_BACKOFF_MS = 1_000` (`:33`) forever with no attempt ceiling and no terminal state. A fix that enlarges the backoff, or that special-cases close code 1013, would not touch the wrong predicate and would leave the five other accept-then-close paths listed in Q-2 storming at 1 Hz.

**F-18.** Chain: `on_client_message` republishes `typing.start` and forgets it (`chatroom.py:75-84`; the only per-connection state is the throttle timestamp `:72-73`) -> the connection closes -> `on_close` calls `presence.leave`, which returns `left=False` when a sibling connection remains (`presence.py:139-141`) -> the `if left:` guard at `chatroom.py:136` suppresses `presence.left`, and no branch publishes `typing.stop` under any condition -> the client's only two clear paths (`useChatroomSocket.ts:216-224`, cases `presence.left` and `typing.stop`) are both starved, and neither the store (`stores/conversation.ts:41-52`) nor the server holds an expiry.

**Root cause: typing state is scoped to a connection but is never retracted when that connection ends.** Presence solves the same problem correctly by refcounting connections; typing was simply never given the symmetric teardown. `resyncPresence`'s `store.clearTyping(roomId)` (`useChatroomSocket.ts:111`) is not a fix, it is an incidental sweep whose frequency happens to be supplied by F-1.

## 6. Blast Radius and Sibling Suspects

**Blast radius**

- F-1 affects every connected client on every one of the eight WS endpoints, continuously. All of them funnel through `connection_loop` and therefore through the same reaper: `app/api/ws/chatroom.py:144`, `user.py:33`, `workflow_runs.py:47`, `prompt_assistant.py:45`, `admin_tail.py:27`, and `rag_configs.py`/`graphrag.py`/`knowmap.py` via the shared scaffold at `contexts/knowledge/interfaces/ws_config_route.py:100`. The client fix lands in `Channel`, which every one of them reaches through `wsManager.channel` (nine call sites, listed in §4 step 1 and in the transport module), so a single change covers all eight.
- F-4 costs server work proportional to the number of over-cap users and leaves those users with a flickering indicator and no polling fallback. It self-resolves only when a tab is closed.
- F-18 affects other room members' view of a multi-connection user. `ChatroomView.vue:683` filters `uid !== myId`, so the typist's own sibling tab is unaffected.
- **No persisted data is affected by any of the three.** The presence keys are Redis-only and self-expiring (`presence.py:35-36`), the per-user cap ZSET prunes by score and carries its own TTL (`connection.py:139,150`), and `_notify_presence` writes nothing durable today (`chatroom.py:32-43`). No data repair is required; see §7.

**Sibling suspects**

The important sweep for this dossier is not "where else does this bug pattern appear" but "what else does the two-minute reconnect currently repair that the F-1 fix takes away". Every branch of the connect handler at `useChatroomSocket.ts:347-356` was walked:

- `stopPolling()` (`:349`) - **cleared.** Symmetric with `onDegraded` (`:359-363`); polling starts and stops on the degraded edge, not on a reconnect cadence.
- `store.clearAllAgentThinking` / `store.clearAgentStream` / `clearThinkingTimeout` (`:350-352`) - **CLEARED IN ERROR — see FU-8.** The reasoning below is correct as far as it goes but answers only half the question, and the missed half is a live regression. Left unedited as the record of the mistake. These clear a stuck thinking spinner, but they are not the only mechanism: the client-side watchdog at `:160-170` (`AGENT_THINKING_TIMEOUT_MS = 120_000`) is a plain `setTimeout` re-armed by `agent.thinking`/`agent.token` and independent of the socket's lifecycle, so a wedged turn is still cleared without any reconnect. Longer-lived sockets do not create a new stuck-spinner path.
- `replayDelta()` (`:353`) - **cleared.** It runs on every reconnect, including the rarer post-fix ones, and also on `message.created` (`:179`) and on the degraded poll timer (`:54`). Its append-only limitation (missed edits and tombstones) is F-11 and is unchanged in kind by this fix; only its trigger rate falls. See Q-1(b).
- `resyncPresence()` -> `store.setPresence` (`:110`) - **cleared.** The client roster can only drift when a `presence.joined`/`presence.left` frame is lost, which requires a disconnect, and every disconnect is followed by a reconnect that refetches the authoritative roster. The repair is coupled to the fault, not to the cadence.
- `resyncPresence()` -> `store.clearTyping` (`:111`) - **CONFIRMED.** The only state whose repair is coupled to the cadence rather than to the fault. This is F-18 and it is fixed in this change. The call itself is kept (see §7).
- `resyncActivation()` (`:355`, `:117-133`) - **cleared.** Same shape as presence: generation-guarded refetch on connect, self-repairing after any gap.
- Approvals - **cleared as a sibling of *this* change** (it is F-13, owned by the reconnect dossier). Nothing in the connect handler ever resynced approvals (`:340-357` never touches `orchStore`; its only writers are the `approval.*` cases at `:268-291`), so the F-1 fix removes no repair for them.

For F-4, the accept-then-close pattern was swept across `connection_loop`: `:234` (`on_open` failed, 1008), `:283` (frame too large, 1008), `:329` (slow consumer, 1013), `:372` and `:406` (token expired/revoked, 4401), `:388` (room access revoked mid-socket, 4403). All six are **confirmed** to produce the same false `onopen` success signal and all six are corrected by the same predicate change; the mid-socket 4403 additionally self-corrects on the next attempt because the handshake ACL check closes pre-accept (`chatroom.py:65-66`). Pre-accept closes (`chatroom.py:51,66`, `user.py:26,31`) are **cleared**: they never fire `onopen` and already back off correctly, which is the contrast that identified the defect.

## 7. Fix Design

**F-1 - send the heartbeat the protocol already defines.** In `frontend/src/shared/transport/ws-manager.ts`, add `HEARTBEAT_INTERVAL_MS = 30_000` and a per-`Channel` interval armed in `socket.onopen`, cleared in `socket.onclose`, `disconnect()` and `close()`, whose callback sends `{ type: 'ping' }` through the existing `send()` (which already guards on `readyState === OPEN`, `:95-99`). Nothing changes on the server: `connection.py:298-300` already answers with `pong`, `:287` already refreshes the cap ZSET score on any inbound frame, and `chatroom.py:86-93` already refreshes room presence through `on_heartbeat`. Placing it in `Channel` rather than in a composable is required by R24.14 (`REQUIREMENTS.md:1852`) and is what makes one change cover all eight endpoints.

This corrects rather than masks because it restores the missing half of a two-sided protocol and re-establishes the invariant the surrounding code was written against. The alternative of raising or removing `_IDLE_TIMEOUT_SECONDS` would mask it and cause two new defects: half-open sockets would hold their per-user cap slot for the full `_CONN_STALE_SECONDS = 300` window instead of 120 seconds (`connection.py:78-83`), and the presence conns TTL would still lapse under a live socket, because `on_heartbeat` runs only on inbound frames (`connection.py:288-292`) and `_CONN_TTL_SECONDS = 150` was sized against a heartbeat that would then still not exist (`presence.py:31-35`). The fix repairs that TTL relationship as a direct consequence.

**F-4 - make "successfully connected" mean the server let the connection live.** Add `STABLE_CONNECTION_MS = 5_000` and a `stableTimer` field. `socket.onopen` keeps `emitStatus(true)` and `scheduleTokenRefresh()` and now also arms `stableTimer`; the three lines that currently reset state at `:136-138` move into that timer's callback. `socket.onclose` clears `stableTimer` before calling `scheduleReconnect`, so a socket that dies before it stabilizes is counted as another consecutive failure and the existing doubling at `:229` runs uninterrupted. `disconnect()` and `close()` clear the timer alongside the existing ones (`:172-184`, `:186-197`).

Result for the reproduction in §4: retries at 1s, 2s, 4s, 8s, 16s, 30s, 30s, with `setDegraded(true)` firing on the third failure, which starts the 10 second REST poll and shows the banner specified at `docs/UI/12-shared-patterns.md:444`. The user's room keeps updating and the pill stops flickering, and the server load falls by roughly 30x. This corrects rather than masks because it replaces a wrong predicate with the right one instead of tuning the curve around it; §6 lists the six accept-then-close sites that a cap-specific or code-specific patch would have left untouched. ## 9. Risks and Rollback

- **Sockets now live for hours instead of two minutes.** Paths that were previously exercised every 121 seconds are now exercised rarely: the in-socket token refresh at ~840 seconds (`ws-manager.ts:242-256`, `connection.py:301-319`) becomes the routine path rather than a corner case, and the auth watchdog (`connection.py:359-407`) becomes the primary revocation enforcement instead of a backstop that a reconnect would have covered anyway. Both are already covered by `test_ws_auth_watchdog.py`. Mitigation: run that file plus a manual soak of one socket across a token expiry boundary.
- **Timer throttling in background tabs.** A 30 second nominal cadence is throttled to roughly 60 seconds in a hidden tab, still inside the 120 second reap window. A frozen or discarded tab stops pinging and is reaped, which is correct behavior, and the channel reconnects on resume through `onMounted`/`onActivated` (`useChatroomSocket.ts:365-371`). Accepted, not mitigated.
- **Degraded clears 5 seconds later than before.** `setDegraded(false)` moves from `onopen` into the stability timer, so REST polling overlaps a recovered socket for up to 5 seconds (`useChatroomSocket.ts:359-363`). The overlap is idempotent: the poll calls `replayDelta`, which is append-only and generation-guarded (`:92-95`). The pill is unaffected because `connectionState` prefers `baseState` once it is `live` (`:39-41`).
- **A flapping-but-real network could now stay degraded longer**, because a connection that survives less than 5 seconds no longer counts as a success. That is the intended semantics; degraded is advisory and the socket keeps retrying underneath (`ws-manager.ts:36-37`).
- **Load direction is favorable, not risky.** Per socket the fix replaces a full reconnect every 121 seconds (ticket mint, handshake, cap ZSET prune/add/card/expire, two presence Lua evals, three HTTP resyncs) with one ping every 30 seconds (one ZSET touch plus one pipelined presence refresh). Watch `WS_CONNECTIONS_ACTIVE` (`connection.py:226`) and `WS_PER_USER_REJECTIONS` (`:213`) after deploy: the first should stop sawtoothing and the second should fall to near zero.
- **The cap state can stick if the clear path is wrong** (Q-5). It is cleared only in the stability timer and in `disconnect()`, so a bug that never arms the stability timer would leave the pill reading "connection limit" on a healthy socket — a worse failure than the one being fixed, because it is silent and wrong rather than noisy and right. Test 10 exists specifically to lock the clear, and AC-12 verifies it end to end against a real recovery.
- **A stale UI-doc table was found, not caused** (Q-5). `docs/UI/07-conversation.md:1041-1045` lists three pill states while the code has four. This change makes it five and repairs the omission in passing; noted so a reviewer reading the diff does not attribute the `degraded` row to this task.
- **Rollback**: the three defect fixes are additive and independent, confined to `ws-manager.ts` and `chatroom.py` plus one comment in `connection.py`, with no migration and no persisted state. The Q-5 addition is separable in the other direction: it depends on the F-4 stability window, so it must be reverted before (or with) F-4, never after it alone. Revert the commit. Note that reverting the F-1 fix alone restores F-18's mask, and reverting the F-18 fix alone re-exposes it; revert them together or not at all.

## 12. Deviation Log

- **D-1 — an extra guard in `socket.onclose`, not in the §7 design.** Found by re-reading this task's own diff. `disconnect()` closes the socket asynchronously while `connect()` awaits an HTTP ticket, so a replaced socket's `onclose` can land after its successor is already open; the handler then tore down the live socket's timers. The hazard pre-existed for the refresh timer, but §7's heartbeat made it materially worse — a cleared heartbeat leaves a healthy socket silent until the server reaps it at 120s, which is exactly the churn F-1 removes. `onclose` now returns early when `this.socket` is a *different* socket, while a null `socket` (a deliberate disconnect/close) still reports as before. Locked by a test that was confirmed to fail without the guard. Committed separately as `fix(frontend): ignore a close from a socket the channel already replaced`.
- **D-2 — `typing.stop` is published after `presence.leave`, not before it.** §7 says the retraction goes "before and independently of the `if left:` guard". It is independent of that guard, as specified, but sits after the `presence.leave` call rather than before it: if the publish raises, running `leave` first means the connection is still released from the roster instead of lingering as a ghost until its Redis TTL. The §7 requirement is about the guard, not the call, so this satisfies the design; recorded because the ordering was a deliberate choice rather than an accident.
- **D-3 — one test beyond §8's list.** §8 item 2 covers "stops pinging once the socket closes", but AC-2 also requires stopping on `disconnect()` and `close()`. Added `stops pinging on disconnect() and on close()` to cover the other two paths.
