# Activities Plugin SDK — frontend `slices/activities`

## 1. Summary

Add a new frontend slice `slices/activities` that renders structured activities inside the
chatroom via a **plugin host**, a **plugin SDK** (a TypeScript contract
`defineActivityPlugin({manifest, schema, render, emit})`), and a **generic JSON-schema form
renderer** fallback for types that need no custom UI. The host mediates **all** API calls with
the user's auth (a plugin never touches the session or network directly) and enforces
server-side scoring authority: a plugin only `emit`s a raw payload; the score comes back from
the backend. v1 runs **first-party bundled** plugins only; the postMessage/iframe contract is
fixed from day one so an untrusted-plugin sandbox can be switched on later without
rearchitecture — but that sandbox's *enforcement* is this dossier's one explicit deferral (it
only matters once outside parties upload plugins). The NSTC component-manipulation canvas is
the first first-party plugin; because it captures the manipulation (rotation angle, chosen
components) as structured facts, the project's "six response categories" become deterministic
UI data, not free-text.

## 2. Goals and Non-goals

**Goals**
- New slice `slices/activities` wired into router, `main.ts` install, and the
  `eslint.config.js` `SLICES`/`SLICE_DEPS` registry.
- Plugin SDK contract `defineActivityPlugin(...)` + a plugin registry for first-party plugins.
- A plugin **host** component that mounts a plugin for an `ActivityType` in the chatroom and
  mediates its API calls (submit, session start) through the slice `api/` wrapper (auto-authed
  via the shared axios interceptors).
- A generic JSON-schema **form renderer** (fallback UI) driven by `ActivityType.payload_schema`.
- WS handling for `activity.created` / `activity.validated` (extend the room socket switch).
- The postMessage host↔plugin **contract** defined and documented from day one (message
  kinds, no direct network/session access, host-mediated calls), even though v1 mounts plugins
  in-process (trusted).
- i18n, boundaries, and the "no bare strings" gate satisfied.

**Non-goals** (explicit deferral, recorded so it is not lost)
- The **iframe sandbox enforcement** for untrusted/uploaded plugins. v1 runs first-party
  bundled plugins mounted in-process; the contract is sandbox-ready but the sandbox is not
  switched on. This is the one deferral and it is deliberate: it only matters when third
  parties can upload plugins that render in other users' authenticated browsers.
- The NSTC component canvas plugin itself and any creativity UI — that is a first-party
  **project plugin** authored against this SDK, not platform code.
- Backend changes — all covered by the core dossier (this consumes its API).

## 5. Design

### 5.1 Plugin contract (fixed day one)

```ts
// slices/activities/sdk/defineActivityPlugin.ts
export interface ActivityPluginManifest { key: string; version: string; title: string }
export interface ActivityRenderCtx {
  schema: JSONSchema                    // the ActivityType.payload_schema
  session: { activityTypeKey: string; sessionId: string | null }
  emit(payload: unknown): Promise<ActivitySubmissionResult>  // host-mediated submit
  t(key: string, named?: Record<string, unknown>): string    // scoped i18n
}
export interface ActivityPlugin { manifest: ActivityPluginManifest; schema?: JSONSchema
  render(container: HTMLElement, ctx: ActivityRenderCtx): void | (() => void) /* teardown */ }
export function defineActivityPlugin(p: ActivityPlugin): ActivityPlugin { return p }
```

**Host-mediation invariant — surface vs enforcement (be precise).** The SDK *surface* hands a
plugin only `emit(payload)`, `t()`, `schema`, and `session`; the intended I/O path is `emit` →
the slice `api/` wrapper (auto-authed). The plugin cannot *submit* a score — `emit` sends the
raw payload and the authoritative `is_valid`/`sub_scores` come back from the backend
(`[R30.03]`), which is a **server-side** guarantee that holds regardless of what the client
does.

What v1 does **not** guarantee: an in-process bundled plugin runs in the same JS realm and can
technically reach `window`, imported modules, or axios if it tries. Non-reachability is
enforced only by the `IframeBridge` (deferred). **v1 relies on first-party trust** — the
plugins are ones we ship. The contract is written so that *nothing in a well-behaved plugin*
touches anything but the four `ctx` members, so switching to the enforcing sandbox later
requires no plugin rewrite. Do not describe v1 as sandboxed; it is trusted-in-process with a
sandbox-ready contract.

### 5.2 Host

`ActivityHost.vue` takes an `ActivityType` + a chatroom/session and:
1. Looks up a registered first-party plugin by `manifest.key`; if none, renders the
   **generic form renderer** from `payload_schema`.
2. **v1 (trusted, in-process):** mounts the plugin by calling `plugin.render(el, ctx)` directly;
   `ctx.emit` → slice `api/submitActivity`.
3. **Sandbox-ready seam:** the same `ctx` shape is what a future iframe bridge will serialize
   over `postMessage`. Define the message kinds now — `{kind:'emit', payload}` (plugin→host),
   `{kind:'result', result}` / `{kind:'schema', schema}` (host→plugin) — and route v1's
   in-process calls through a thin `HostBridge` interface with two implementations declared:
   `InProcessBridge` (v1) and `IframeBridge` (stub, deferred). Switching later = swapping the
   bridge impl, not the host/plugin.

### 5.3 Generic JSON-schema form renderer

`SchemaForm.vue` renders `payload_schema` (object with typed properties) into `shared/ui`
atoms (`SFormField` + `SSelect`/inputs), validates client-side with a Zod schema **derived from
the JSON schema** (for UX only — the server re-validates authoritatively), and `emit`s the
object. Scope v1 to the property types the project needs (string, number, boolean, enum,
array-of-enum); unsupported constructs fall back to a labelled JSON textarea (never silently
drop a field).

### 5.4 Realtime + state

Extend the room socket switch (`useChatroomSocket.ts` before `default` `:270`) with
`activity.created` / `activity.validated`, updating an activities store (`stores/activities.ts`)
keyed by submission id so a `pending → validated` transition updates the rendered outcome.
Follow the `approval.*` cross-slice-store precedent (`:246-269`). Because the switch lives in
`slices/conversation`, the handler either lives there importing `@slices/activities` (allowed
once conversation depends on activities, Q-3) or the store lives in `@shared/stores`.

## 8. Security Considerations

Touches untrusted-content rendering, WebSocket, user auth, and plugin execution — full lens:
- **Server-side scoring authority (enforced at the contract).** The plugin `emit`s only a raw
  payload; it has no path to submit a score. `is_valid`/`sub_scores` are backend-computed
  (`[R30.03]`). A tampered client cannot inflate a score.
- **Scoring authority is the real guarantee.** The one property that holds against a *malicious*
  client is server-side scoring: `emit` submits only a raw payload and the score is computed on
  the backend (`[R30.03]`). No client — plugin or tampered browser — can inflate a score. This
  is independent of the sandbox.
- **Host-mediated I/O is the intended path, not v1-enforced.** The SDK gives a plugin only the
  host `emit`; a well-behaved plugin never touches axios/session/WS. But in v1 (in-process) this
  is a *contract*, not an *enforced boundary* — an in-process plugin shares the page's realm.
  See §5.1. This is acceptable **only because v1 plugins are first-party/trusted**.
- **v1 trust boundary is explicit, and the sandbox is a hard gate on untrusted plugins.** First-
  party bundled plugins run in-process (same origin/privileges) — acceptable because we ship
  them. **Before any untrusted/uploaded plugin may render in another user's authenticated
  browser, the `IframeBridge` (sandboxed `iframe` with `sandbox="allow-scripts"`, postMessage-
  only, no same-origin) MUST be switched on** — that is the deferred item; this dossier fixes the
  contract so the switch is a bridge swap, not a rearchitecture. Recorded as FU-1.
- **Schema-driven rendering, no injection.** `SchemaForm` renders into `shared/ui` atoms; any
  free text a plugin displays must go through the existing DOMPurify pipeline
  (`renderMarkdown.ts:84`, which already forbids `iframe`/`script`). No `v-html` outside the
  existing allowlist (`eslint.config.js:226-244`).
- **WS handling is read-only display.** `activity.*` events update local state only; no event
  payload is trusted for authorization decisions.

## 10. Risks and Rollback

- **Greenfield host/bridge** — no in-tree precedent (confirmed). Mitigate by keeping v1
  in-process and the bridge interface minimal; the iframe impl is deferred, so v1 risk is a
  normal Vue component.
- **Dependency-direction change** (`conversation → activities`) touches the boundaries config;
  verify no cycle is introduced (activities must not depend back on conversation for rendering).
- **Schema-renderer scope creep** — cap supported JSON-schema constructs (§5.3) and fall back
  to a JSON textarea; do not attempt a full JSON-schema form engine.
- **Rollback**: the slice is additive; removing its `main.ts`/router wiring and the
  conversation dep disables it. WS cases fall through to `default`.

  `schemaForm.ts` as the design implied. `SchemaForm.vue` + `schemaForm.ts` collide
  case-insensitively on Windows, which broke module resolution and the composite-project file
  list (`vue-tsc` TS6307). Renamed to `schemaFields.ts`; behavior identical.

  vee-validate's `toTypedSchema` that §9's reuse inventory suggested. §5.3 only requires "a Zod
  schema derived from the JSON schema (for UX only)"; a fully-dynamic vee-validate `useForm` adds
  complexity with no spec benefit. The derived-Zod requirement is met; the server remains
  authoritative.
- D-3 (freshness, no behavior change): §4 cited the `SLICES`/`SLICE_DEPS` registry as 8 slices;
  the live registry has 10 (adds `agent-groups`, `prompt-studio`) and `conversation` already
  depended on `agent-groups`. Followed the current registry: added `activities` to `SLICES`,
  `activities: []` to `SLICE_DEPS`, and prepended `activities` to `conversation`'s deps. The
  one-way `conversation → activities` edge (Q-3) is unchanged in intent.
- Note (not a deviation): `ActivityHost` is exported but not embedded into `ChatroomView`.
  Consistent with §6 (which lists no `ChatroomView` edit) and the non-goals — the in-room

## 16. Follow-ups

- FU-1: Enable the `IframeBridge` (sandboxed iframe, postMessage-only) and an upload/vetting
  flow — required before any untrusted third-party plugin may render in another user's
  authenticated browser. Deferred deliberately (no threat until uploads exist); the contract in
  this dossier makes it a bridge swap, not a rearchitecture.
- FU-2 (backend): The WS `activity.validated` event carries only `{submission_id,
  validation_status}` — no `is_valid`/`sub_scores`. After **async** (mcp/webhook) validation the
  frontend can therefore show the validated/error *status* but not pass/fail without a refetch,
  and there is no single-submission GET. Moot for v1 first-party **in-process** validators (the
  submit HTTP response already carries `is_valid`). When async validators drive first-party UI,
  enrich the event with `is_valid`/`sub_scores` or add a submission GET; the store already keeps
  richer local data and would consume it with no reducer change.
- FU-3: The in-chatroom **activation UX** — where/when an activity becomes active in a room,
  opening/closing an `ActivitySession`, and mounting `ActivityHost` inside `ChatroomView`. This
  task delivers the host + SDK as consumable pieces; the trigger and session lifecycle are the
  next slice of work.
